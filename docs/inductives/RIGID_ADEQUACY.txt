RIGID APPLICATION ADEQUACY AUDIT (2026-10-05)

Target

Typing/Injectivity.lean, IsDefEqU.rigidApp_inv, assumes only an ordered/WF
environment, a well-formed caller context, Rigid c, an equality between two
applications of c, and a sort typing for the left application. Its conclusion
compares ALL universe arguments and ALL term arguments. It does not require a
registered structure, a literal sort-ending declaration telescope, or any
supplied family query.

Current conclusion

The all-budget world interfaces now have actual initial identity frames and
sort/Pi/assigned-conversion adequacy bridges. The existing family query seed
construction does not yet cover this exact public rigid-application target.
The decisive gap is a declaration type whose result becomes a sort only AFTER
its actual arguments are substituted. This is a query-construction gap, not a
counterexample to rigid injectivity and not a proof that the all-budget banks
logically cannot imply the target by some different argument.

Concrete example

Use a fresh rigid axiom c with no defining equation and declared type

  c : Pi (A : Sort 1), A.

Then c (Sort 0) : Sort 0 is derivable by the ordinary constant, sort and
application rules. The environment may have no definitional equations at all.
Rigidity is then vacuous. The literal declared telescope has domains=[Sort 1]
and result=#0. After the actual argument is substituted, result becomes Sort 0.
Before substitution it is not syntactically any sort. Choosing a shorter or
longer ConstantTelescope cannot fix this: the only other prefix is empty with
a Pi result; #0 cannot be peeled as another Pi.

The issue does not rely on an axiom asserting an inhabitant of every type.
A rigid opaque identity constant

  c : Pi (A : Sort 1), A -> A

and a rigid p : Sort 0 give c (Sort 0) p : Sort 0. The fully peeled declaration
result is again a bound variable (#1), not a literal sort.

These are mathematical instances of the ordinary typing rules, not a newly
added kernel-checked counterexample file. No grammar or global motive was
changed for this audit.

Alternate routes checked

1. RichObs.code / RichCert.observe and legacy code/ofCode/seed wrappers:
   these require a finite child observation/certificate at the SAME expression.
   They do not reflect an arbitrary TypeRelated proof into query syntax.
   Following their child does not supply the missing family leaf.

2. RichObs.app / legacy application:
   a desired family result requires the actual function child to carry a
   function query whose output is that family demand. Following the finite
   application spine reaches the same constant-leaf family-plan requirement.
   Selecting an actual appPrefix changes retained original endpoint metadata,
   not the constant's syntactic declaration telescope.

3. RichCert.pi / ordinary Pi seeds:
   they observe literal Pi expressions, not the rigid application c args.
   Sort seeds analogously observe a literal sort. PrefixRoute preserves the
   expression and cannot cast #0 or c args to a literal sort expression.

4. RichCodeRecipe:
   domain/body/fixedBody/resources/action all retain a root ancestor. The root
   requires CanonicalCodeOwner, which contains a present environment equation.
   In the no-equation example there is no such owner. An arbitrary fresh
   synthetic owner is not allowed. Even when an unrelated owner exists, it
   still needs a finite actual closed certificate; a recipe does not itself
   turn raw formation into a family atom.

5. canonicalConst / canonicalDelta / legacy delta and native:
   canonical wrappers retain actual owner/equation provenance. Delta needs a
   registered equation. In the example choose the empty definitions/native
   registry and an equation-free environment, eliminating these alternatives.
   Canonical wrappers cannot be manufactured solely because c is closed.

6. Constructor observations:
   their terminal requires the declared result to be literally family-headed
   (or the corresponding record constructor condition). The bound-variable
   result in the example fails that requirement as well. A ctor atom is not
   itself a family-code observation of c args; its family support still has
   to be constructed from an actual child certificate.

7. union/select/pad/down/view/support/actions:
   these transform or select existing finite observations. AtomView's changes
   are function reanchoring/rekeying/input changes and lifted compositions;
   it has no arbitrary sort-to-family constructor. SortableCodeAction.atom
   retains a selected source atom, including focusMinimal. familyPad requires
   an existing family atom. These operations provide no fresh rigid-family
   leaf from an empty or literal-sort query.

8. Captured-variable escape:
   one can syntactically ask for any family profile at a variable, but using
   a positive captured frame to display that variable as c args requires the
   stored owner observation at c args. That is the original missing seed.
   A plain identity graph cannot identify its literal common variable with
   the distinct closed-headed application in ordinary same-display R.
   Constructing a semantic diagonal family witness and installing it as an
   arbitrary query/frame answer would be an extra semantic-to-syntax premise,
   not the current operative producer.

This is a source inspection and exact failed constructor obligation, not a
formal impossibility theorem for every conceivable query/program encoding.

Remaining full-target requirement

An arbitrary rigid declaration can also hide a Pi in a reducible header, e.g.
a rigid c : D where D unfolds to a Pi. terminalTyped alone cannot make a
ConstantTelescope for that syntactically non-Pi declaration contain the needed
binder. The minimum full representation must therefore retain the finite
ACTUAL typed application spine, including genuine original header/assigned
conversion routes at each exposed Pi, and the residual sort observation after
actual anchors are substituted. Actual input derivations have appPrefix and
constantPrefix nodes that can drive this finite exposure; no independent
normalization oracle or arbitrary normalized-header cast is justified.
