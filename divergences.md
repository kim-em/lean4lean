# Divergences from the Lean Kernel

This is a list of places where lean4lean deliberately has different behavior from the kernel. Unless specified here, any divergence between lean4lean and [lean4](https://github.com/leanprover/lean4/tree/master/src/kernel) is a bug.

* [`Lean4Lean.TypeChecker.Inner.reduceNative`](Lean4Lean/TypeChecker.lean): Lean4lean does not support reduction of `reduceBool`. This would involve implementing verified compilation, which while possible would be an additional chunk of work comparable to this entire repo.
* [`Lean4Lean.Primitive.checkDef`](Lean4Lean/Primitive.lean), `checkInductive`: Lean does not check that primitives are declared with the correct types and definitional behavior, except in the case of `Eq` which is used in the declaration of `Quot`. This is required for soundness, but Lean is able to get away with it because Lean ships its prelude and using an alternative prelude is not supported.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), literal case: The original code was not checking that the literal type actually exists. Again, this is okay provided that the prelude is trusted.
* [`Lean4Lean.TypeChecker.Inner.tryStringLitExpansionCore`](Lean4Lean/TypeChecker.lean): there is a counterproductive `whnf` call in this function which is removed in Lean4lean.
* [`Lean4Lean.TypeChecker.Inner.isDefEqApp`](Lean4Lean/TypeChecker.lean): lean4lean compares the two argument counts before the two heads, where `type_checker::is_def_eq_app` compares the heads first. Both answer `false` when the counts differ, so the decision is the same.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), application case: lean4lean checks `isDefEq dType aType`, where `infer_app` checks `is_def_eq(a_type, d_type)`. Definitional equality is symmetric, so this cannot change the answer, but this avoids some needless left-right flipping.
* [`Lean.Level.normalize`](https://github.com/leanprover/lean4/blob/v4.33.0-rc2/src/Lean/Level.lean), `isEquiv`, `geq`, `instantiateLevelParams`: Lean4lean uses the level operations from Lean's standard library, which differ from the C++ kernel's; [leanprover/lean4#14356](https://github.com/leanprover/lean4/pull/14356) tracks aligning them. This has two separate consequences. The comparison operations decide slightly different sets of (in)equalities than the kernel's `is_equiv`/`is_geq` (but see the next point). And because `instantiateLevelParams` builds levels with `mkLevelMax'`/`mkLevelIMax'` rather than the kernel's `mk_max`/`mk_imax`, unfolding a universe-polymorphic constant can produce a term that means the same as the kernel's but is not syntactically equal to it, and so does not share its `Expr.hash`.
* [`Lean.Level.normalize'`](Lean4Lean/Level.lean), `isEquiv'`, `geq'`: Lean4lean implements a new algorithm for level normalization. These run the standard library's operation as a fast path and fall back to a complete decision procedure for level algebra, so lean4lean decides level equality and `≥` for *more* pairs than either the standard library or the kernel — it accepts declarations the kernel rejects for reasons of level incompleteness, never the other way around.
* [`Lean4Lean.checkConstantVal`](Lean4Lean/Environment.lean): The original implementation would call `check` which sets the level params and then unsets them afterward, and then `ensure_sort` would run in a context without any level params. In lean4lean the monad is parameterized over level params, so they remain the same across the two calls.
* [`Lean4Lean.TypeChecker.Inner.inferProj`](Lean4Lean/TypeChecker.lean), [`toCtorWhenStruct`](Lean4Lean/Inductive/Reduce.lean): both kernels recognize `Prop` up to universe normalization ([leanprover/lean4#14613](https://github.com/leanprover/lean4/pull/14613)), but they differ on levels that are neither always nor never zero: lean4lean tests `isNeverZero` where Lean tests `!isAlwaysZero`. Lean4lean's rule requires the structure's universe to be never zero at the projection's particular universe instantiation. This does not make every accepted projection expressible with the exact recursor generated before specialization. For `MaybeProp.{u} : Sort u` with a field in `PUnit.{u}`, the kernel cannot rule out that the type is a proposition, so it emits `MaybeProp.rec : {motive : MaybeProp → Prop} → ...` — small elimination only — and `fun x => x.0 : MaybeProp.{u} → PUnit.{u}` cannot be written with it. Lean accepts that projection anyway, so under Lean's rule `proj` computes something the type's own eliminator cannot. Lean's choice is still sound, but only because the constructor universe bound in `inductive.cpp` separately rejects `inductive T.{u} : Sort u where mk : Bool → T`, which would otherwise give an analogue of the construction in #14613; testing `isNeverZero` makes the projection check independent of that bound. Even with this check, specializing a sort-polymorphic box to `Sort 1` permits a large projection while its native recursor remains restricted to `Prop`; `Tests/ProjectionSpecialization.lean` exercises this case. Projection desugaring needs an abstract eliminator schema with admissibility checked after specialization. Reconciling the two in the other direction — letting the recursor eliminate large whenever every field's universe is bounded by the inductive's, which is exactly what makes such a projection sound — would be the complete answer, but that is a change to recursor generation rather than to this check.
* [`Lean4Lean.TypeChecker.Inner.reduceProjCore`](Lean4Lean/TypeChecker.lean): when reducing `.proj S i e` with `e` a constructor application `c args`, lean4lean additionally requires `c` to be the unique constructor of `S` (the C++ kernel checks `c`'s inductive against `S` since [leanprover/lean4#14632](https://github.com/leanprover/lean4/pull/14632)) and `args` to have exactly `numParams + numFields` entries. On well-typed input both checks are redundant, because `inferProj` has already matched `S` against the type of `e` and a constructor application of any other arity does not have an inductive type; they let the verification justify the reduction from the projection registry of `S` alone, without relying on injectivity of inductive type applications or on an inductive type not being a function type.
* [`Lean4Lean.TypeChecker.Inner.tryEtaStructCore`](Lean4Lean/TypeChecker.lean): lean4lean additionally requires the constructor at the head of `s` to be the constructor listed by its inductive type (a well-formed environment never lists another one), and only applies structure eta when the sort of the structure type is never zero, where the C++ kernel applies it to any non-recursive structure. When the type is a proposition, `isDefEqProofIrrel` has already decided the comparison, so the difference is confined to structures in a universe that is neither always nor never zero (`Sort u`), exactly as for `inferProj` above: there the projections `tryEtaStructCore` compares may not be well typed, and the verified checker never compares ill-typed terms.
* [`Lean4Lean.TypeChecker.Inner.inferProj`](Lean4Lean/TypeChecker.lean): lean4lean rejects `.proj S i e` when `i` is not below the constructor's recorded `numFields`, where the C++ kernel only walks the constructor telescope. The telescope walk fails in the same cases on a well-formed environment (the recorded field count is the length of the telescope), so this only changes the error reported; it keeps the verification from needing that a whnf-normal form of the constructor's result type is not a `forallE`.
* [`Lean4Lean.TypeChecker.Inner.reduceProjCore`](Lean4Lean/TypeChecker.lean), [`tryEtaStructCore`](Lean4Lean/TypeChecker.lean), [`isDefEqUnitLike`](Lean4Lean/TypeChecker.lean), [`expandEtaStruct`](Lean4Lean/Inductive/Reduce.lean): lean4lean additionally requires the constructor found for a structure to record that structure as its owner (`induct`) and to agree with it on `isUnsafe`. Both hold on every environment the kernel produces; they let the verification identify the projection registry entry of the family from the constructor's presence alone, in particular transferring the constructor's visibility at the current safety level to the family.
* [`Lean4Lean.toCtorWhenK`](Lean4Lean/Inductive/Reduce.lean): lean4lean additionally requires the whnf of the major premise's type to apply the major inductive to exactly `numParams + numIndices` arguments before building the nullary constructor application (the C++ kernel takes whatever parameters are present). A type applying it to any other number of arguments is not a type, so this cannot change the answer on well-typed input. The metavariable check over the index arguments is written as `Array.any` instead of a loop with early return; it is the same test.
* [`Lean4Lean.toCtorWhenStruct`](Lean4Lean/Inductive/Reduce.lean), [`expandEtaStruct`](Lean4Lean/Inductive/Reduce.lean): lean4lean returns the term unchanged where the C++ kernel has `unreachable!` (the constructor of a structure is not a constructor of the environment; the type of the type does not whnf to a sort), and additionally leaves the term unchanged when its type applies the structure to a number of arguments other than `numParams`. Both are unreachable on well-formed environments and well-typed terms; the fallbacks keep every branch of the conversion sound by construction.
* [`Lean4Lean.Environment.restoreNestedAfterInstall`](Lean4Lean/Inductive/Add.lean): the restored recursor rules are validated (`validateRestoredRecursorRules`) in a copy of the restored environment in which every restored recursor carries an empty rule list (`stripRecursorRules`), where upstream's check ([leanprover/lean4#14621](https://github.com/leanprover/lean4/pull/14621)) runs in the restored environment itself. The validation type-checks both sides of each rule; with the rules present, iota reduction of a restored recursor could be used while its own rule is being validated, which the verification cannot justify (the abstract iota equations are only added once the rules are known to be well formed). Stripping the rules makes the check strictly more conservative: a rule whose typing needed a sibling rule's reduction is rejected rather than accepted, and no rule the kernel generates needs one. The returned environment is unchanged.
* [`Lean4Lean.checkNoNestedAux`](Lean4Lean/Inductive/Add.lean): [leanprover/lean4#14616](https://github.com/leanprover/lean4/pull/14616) rejects the reserved `_nested` prefix in both the inductive types and the constructor types of a declaration; lean4lean checks only the constructor types. The bug that check fixes is specific to constructors: nested occurrences are rewritten to the auxiliary types in constructor types only (`replaceAllNested`), and rewritten back the same way (`restoreNested`), so an inductive's own type is carried through both directions verbatim and cannot acquire a type it was not checked at. A `_nested` name written in an inductive type also cannot resolve in the first place: the auxiliary types are declared in the same block, so they are not in the environment while that block's types are checked (unlike constructor types, which are checked once the block's types, auxiliaries included, are present), and they never survive into the final environment. Lean's check additionally reserves the whole `_nested` namespace against unrelated user declarations, which lean4lean does not.
* [`Lean4Lean.ElimNestedInductive.Result.restoreNested`](Lean4Lean/Inductive/Add.lean), `restoreCtorName`: [leanprover/lean4#14632](https://github.com/leanprover/lean4/pull/14632) turned the `lean_assert`s in the nested-inductive restoration into kernel exceptions; lean4lean keeps `unreachable!` and `assert!`. The branches are unreachable: `restoreCtorName` runs only for the recursors of the auxiliary types the elimination generates, whose constructors are exactly the keys of `aux2nested`, and the nested occurrences stored there are applications of a constant by construction. Upstream's stated motivation is that the assertions vanish in a release build and the C++ consumers then read out of bounds; the corresponding accesses here are total, so there is nothing to read out of bounds. Note that if one of these invariants were broken anyway, `unreachable!` would continue with a default value rather than reject; the restored constructor and recursor types are re-checked in the final environment ([#14621](https://github.com/leanprover/lean4/pull/14621)), which lean4lean retains, but a restored rule constructor *name* is not covered by that pass.
* [`Lean4Lean.FuelConfig`](Lean4Lean/FuelConfig.lean): since [leanprover/lean4#13956](https://github.com/leanprover/lean4/pull/13956), the native kernel bounds mutually recursive checking through the `maxRecDepth` option. Lean4lean exposes several independent fuel counters instead, because its Lean definitions also need explicit termination witnesses. Replay comparison therefore uses each implementation's default bound unless an explicit lean4lean fuel configuration is supplied.
* [`Lean4Lean.addDefinition`](Lean4Lean/Environment.lean) (`unsafe` branch), [`addMutual`](Lean4Lean/Environment.lean): an `unsafe`/`partial` definition may be recursive, so its body is checked in an environment that already contains the declaration. The C++ kernel adds `constant_info(d)` there -- the full definition, value included -- so the body can delta-unfold the very constant being defined. Lean4lean adds it as an axiom of the same type instead: the body may still *refer* to the block's constants, but cannot unfold them. So for example `unsafe def foo : Nat := (fun (_ : foo = 1) => 1) rfl` is accepted by the C++ kernel, but rejected by L4L: checking the argument requires `foo =?= 1`, which succeeds by unfolding `foo` to its own body and reducing. Read literally, that rule makes a typing fact about the constant available while establishing it, and implementing this in `IsDefEq` directly degenerates completely, allowing even things like `unsafe def bar : Nat := "hi"` by using the typing judgment to justify itself. The gap is confined to `unsafe`/`partial` code, which carries no logical content.
* [`Lean4Lean.addMutual`](Lean4Lean/Environment.lean): lean4lean requires the declarations of a mutual block to carry the same universe parameters and to have distinct names. Both checks are in kernel PRs that are not yet released ([leanprover/lean4#14608](https://github.com/leanprover/lean4/pull/14608), [#14632](https://github.com/leanprover/lean4/pull/14632)); the released kernel checks only that the safety annotations agree. Lean4lean needs them rather than merely matching them: the block is checked under a single `M.run`, whose level parameters are fixed for the whole run, and the model adds the block's constants one at a time with `VEnv.addConsts`, which fails on a repeated name.
* [`Lean4Lean.TypeChecker.State.leaveScope`](Lean4Lean/TypeChecker.lean), `withFreshId`, `isDefEqLambda`, `isDefEqForall`: every binder the checker opens puts the inference caches, the `whnf` caches, the equivalence manager and the failure cache back to their state before the binder when it is closed (the name generator stays advanced and the `unfold` cache, which depends only on the environment, is kept), and `isDefEqLambda`/`isDefEqForall` compare the bodies under a binder even when neither body mentions it. The C++ type checker keeps its caches and its equivalence manager for the whole run, so a conversion fact established under a binder answers later queries outside it. This can change a decision, and only towards rejection. `docs/inductives/CacheScopeExperiment.lean` builds, in an environment without `Eq`, a closed definition whose value first forces the comparison `SI ≡ SJ` under a hypothesis `q : P v` (inside an otherwise unused `let`) and then uses a term of type `SI` at type `SJ`: the C++ kernel accepts it and rejects the same definition without the seeding `let`; the scoped checker rejects both (lean4lean without scoping accepted it too). `SI ≡ SJ` holds in the context extended by `q` but is not derivable in the outer context (`docs/inductives/STRENGTHENING.md`), so the C++ acceptance uses a conversion fact outside the scope in which it holds: it is the C++ behaviour that is non-local. The verification needs every cache entry to be derivable in the current context (`VState.WF`). Replays of `Init.Prelude` and `Init.Core` are unaffected.
* [`Lean4Lean.AddInductive.Context.checkLCtx`](Lean4Lean/Inductive/Add.lean), `withCheckLCtx`, `withCheckedLocalDecl`, `paramCheckLCtx`: the type checker runs embedded in the inductive checker see a local context holding only the parameters, indices and fields that the run's input can mention, never the majors, motives, minors or induction hypotheses that `inductive.cpp` keeps in `m_lctx`. A checker run looks up only the free variables reachable from its input, and every embedded C++ call constructs a fresh `type_checker`, so no cache is shared between calls; the decisions are the same. (A narrowing that left out a variable the input mentions would make the run fail with an unknown free variable; the replays and `Tests/RecursorOracle.lean` exercise every call site.) The narrowing lets each checker fact be produced in the scope its verification uses.
* [`Lean4Lean.ElimNestedInductive.mkUniqueName`](Lean4Lean/Inductive/Add.lean): the auxiliary types produced by nested-inductive elimination are named `_nested.1`, `_nested.2`, ... (`Name.mkNum`), where `elim_nested_inductive_fn` names them `_nested.J_1`, `_nested.J_2`, ... after the nested family `J` (`append_after`). The fresh-name search is also bounded (by the size of the environment plus one, which always suffices) instead of unbounded. The auxiliary names are internal: they are not in the returned environment, constructor and recursor names are restored from them by prefix replacement, and both kernels skip names already in the environment, so the choice of names cannot change a decision; it is visible only in error messages about auxiliary constructors. The verification relies on the numeric form to separate auxiliary family names from the string-extended names of restored declarations (`Verify/Inductive/Nested/LoweredRulesAvoid.lean`).
* [`Lean4Lean.AddInductive.declareRecursors.checkRecursorTypes`](Lean4Lean/Inductive/Add.lean): each generated recursor type is type-checked (in the empty local context, under the recursor's universe parameters) before the recursors are installed. The kernel of the pinned toolchain (v4.33.0-rc2) installs generated recursors with `add_core` and does not check them; [leanprover/lean4#14808](https://github.com/leanprover/lean4/pull/14808) (v4.35) adds `check_recursors`, which type-checks each recursor type after installation (the same check: a recursor type does not mention the recursors) and also checks that each computation rule is type-preserving (`whnf` of the recursor applied to a constructor has the recursor's result type). Lean4lean does not perform the rule check for ordinary blocks: the verification proves the generated rules correct instead (each installed iota equation is one of the equations of the generative specification), so it would add proof obligations without contributing an invariant. The recursor-type check is not redundant for the verification: its postcondition (`RecursorTypeTranslations`) is how `declareRecursors.WF` obtains the translation and well-typedness of the installed recursor types. On a correctly generated recursor neither check fails, so the decisions agree with both kernels except through checker fuel.
* [`Lean4Lean.AddInductive.mkRecInfos.loopArgs1`](Lean4Lean/Inductive/Add.lean), `loopInd1`, `loopU`, `mkRecRules.loopU`: recursor construction throws when the inductive header has fewer parameters than declared or a different number of indices than `checkInductiveTypes` recorded, and when a field classified as recursive no longer has a valid inductive result type when its type is read again (where `getIIndices` assumed it). These are unreachable: the same headers and field types were normalized the same way by `checkInductiveTypes` and `isRecArg`. They let the verification avoid proving that two normalizations agree.
* [`Lean4Lean.Environment.restoreNestedAfterInstall`](Lean4Lean/Inductive/Add.lean), `validateRestoredConstructorParameters`, `validateRestoredRecursorTypes`: the re-checks of [leanprover/lean4#14621](https://github.com/leanprover/lean4/pull/14621) run in side environments that contain only the restored headers (and, for the recursor types, the restored constructors), not in the complete restored environment; restored constructor and recursor types cannot mention the restored recursors, so the decisions are the same. In addition, lean4lean re-checks the parameter prefix of every restored constructor type against the parameters retained by lowering (`isDefEq` of each domain with the parameter's type), which the C++ kernel does not. The prefix is not rewritten by restoration and was already checked against the same parameters in the lowered block, so this rejects nothing that the C++ kernel accepts except through checker fuel; `Verify/Inductive/Nested/ConstructorParameterValidationSoundness.lean` uses its result.
* [`Lean4Lean.validateRestoredRecursorRules`](Lean4Lean/Inductive/Add.lean) (`checkGuarded`, `checkGuardedWithFieldsAtArity`, `checkPrimaryRuleShape`, `checkEquation`, `checkPrimaryEquation`): upstream ([leanprover/lean4#14621](https://github.com/leanprover/lean4/pull/14621)) only type-checks the right-hand side of each restored rule. Lean4lean additionally checks that every rule is structurally guarded (each restored recursor call in a right-hand side has a constructor field as its major), that a primary rule keeps the exact lambda arity, constructor-field spine and recursive-result arity of the rule generated for the lowered block, and that the literal iota equation is well typed: the left-hand side (the recursor applied to the constructor) and the right-hand side have definitionally equal types, together with typing witnesses for the shared prefix and the body type. These are the facts from which the verification reconstructs the abstract iota equations of restored recursors (`Verify/Inductive/Nested/RestoredEquationWF.lean`, `RuleShape.lean`). Every rule the kernel generates satisfies them, so they reject nothing the C++ kernel accepts except through checker fuel; the restored nested blocks of the `Init.Prelude` and `Init.Core` replays (for example `Lean.Syntax`, nested through `Array`) and `Tests/NestedInductive.lean`/`Tests/NestedRecursorReduction.lean`/`Tests/NestedIndexedFamily.lean` pass them. The left-hand side of an equation takes the constructor's parameters from the major premise's domain, which lies below the recursor's index binders; they are read back at the depth of the rule, which matters for indexed families with parameters (`Tests/NestedIndexedFamily.lean`). The guard traversal expands natural-number and string literals into constructors, so its cost grows with the size of literals in restored rules.
* [`Lean4Lean.validateNestedAuxiliaries`](Lean4Lean/Inductive/Add.lean): the parametric nested applications `I Ds` of [leanprover/lean4#14577](https://github.com/leanprover/lean4/pull/14577) are type-checked, as in the C++ kernel, but in the environment of the restored headers only (the C++ kernel uses the complete restored environment; `Ds` cannot mention the block's constructors or recursors, so the decision is the same). The stored application is `I` applied to its parameters only, so for a nested occurrence of a family with indices it is a type family, not a type, and neither kernel requires a type: `inductive VTree | node : Vec VTree 2 → VTree`, with `Vec : Type → Nat → Type`, is accepted by both, with the same constructors and recursors (`Tests/NestedIndexedFamily.lean`). The verification closes each stored application with lambdas over the parameters, and its inferred type with foralls over the same parameters (`ClosedValidatedNestedAuxiliaries`), so it covers type families as well as types.
* [`Lean4Lean.Primitive.Condition.check`](Lean4Lean/Primitive.lean), [`unfoldNatWellFounded`](Lean4Lean/Primitive.lean): inside the primitive-definition recognizer (itself a lean4lean-only check, see `Lean4Lean.Primitive.checkDef` above), the four closed pieces of a `reflectNatNat` condition are type-checked on their own, and the functional of a well-founded definition is type-checked again (rather than only inferred) in the outer context after the telescope that found it is closed. They only concern definitions with reserved primitive names, which the C++ kernel does not check at all; on the real prelude they succeed. They exist so that no fact established under the gadget's binders is used outside them (see the scoped caches entry above).

* [`Lean.Kernel.Environment.isTypeAnnotationWrapper`](Lean4Lean/Expr.lean), [`Lean.Expr.consumeTypeAnnotationsVerified`](Lean4Lean/Expr.lean), [`Lean4Lean.AddInductive.withConsumedCheckedLocalDecl`](Lean4Lean/Inductive/Add.lean): the inductive checker strips `optParam α d`, `autoParam α s`, `outParam α` and `semiOutParam α` to `α` in binder domains, as `consume_type_annotations` does in the C++ kernel (called from `local_ctx::mk_local_decl`), but only when the environment declares the name as the prelude's definition: a safe definition with universe parameters `[u]` whose type and value are exactly the prelude's (`@[reducible] def optParam (α : Sort u) (default : α) : Sort u := α`, `def autoParam (α : Sort u) (tactic : Lean.Syntax) : Sort u := α`, `@[reducible] def outParam (α : Sort u) : Sort u := α`, and `semiOutParam` like `outParam`). Otherwise the domain is kept and checked literally. The C++ kernel strips by name alone, which is unsound when the name means something else: with `def optParam (α β : Type) : Type := β` declared in an environment without the prelude, it accepts `inductive T | mk : optParam A B → T` and generates a recursor whose minor premise takes an `A` for a constructor field of type `B`; lean4lean keeps `optParam A B` in the constructor and the recursor (`Tests/TypeAnnotationWrappers.lean` checks both behaviours). Both kernels type-check the complete constructor and header types before stripping anything, so an application of an undeclared wrapper name is rejected by both. The constructed recursor therefore differs only on environments that declare one of the four names with another definition, and only there can a decision differ (for example, the universe check of a field reads the stripped domain in the C++ kernel); on every environment in which the wrappers are the prelude's, or are not used, the two kernels strip the same applications and make the same decisions. The lookup only happens when a binder domain is headed by one of the four names. Each strip is justified from the definition looked up at that point (`TypeAnnotationWrappers.of_env`), so the verification needs no invariant on how these names are declared, and the empty environment satisfies `VEnvs.WF` (`VEnvs.WF.empty`).

## Audit of the executable changes of the verified inductive checker

Every behavioural change made to the executable relative to `master` (`Lean4Lean/TypeChecker.lean`, `Inductive/Add.lean`, `Inductive/Reduce.lean`, `Primitive.lean`, `Quot.lean`, `EquivManager.lean`, `Replay.lean`, `Expr.lean`, `ExprUniverses.lean`, `WHNFCacheKey.lean`; `Environment.lean`, `Environment/Basic.lean`, `Level.lean` and `Main.lean` are unchanged). Class (i): same decisions and same constructed terms as the C++ kernel (justification given); (ii): divergence documented above before this audit; (iii): divergence found by the audit and documented above.
